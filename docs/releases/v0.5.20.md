# v0.5.20 — Bounded RAM batches and reduced WAL traffic

Completed document publications collect for up to 10 ms in a plugin-owned RAM buffer. A batch targets at most 64 documents or 8 MiB of estimated input, with an oversized document handled alone. Pending input has a 64-document / 64-MiB admission bound; busy callers receive backpressure rather than unbounded allocations. The flush joins the existing serialized writer, performs one WAL transaction, and isolates individual failures with savepoints. Successful callers resolve only after commit. The writer cache is updated only after commit. Close is idempotent and drains accepted buffered work before releasing SQLite. A queued publication cannot resurrect a deleted document/base.

The writer uses RAM temporary storage and a lazily allocated adaptive SQLite page cache capped at 4 GiB and approximately one sixteenth of available RAM at open (minimum 32 MiB). Reader connections retain their small caches. Automatic WAL checkpoints use 8192 pages (32 MiB with the normal 4-KiB page size). WAL and synchronous=NORMAL remain enabled; no live database is moved to a volatile RAM disk.

Canonical text equality no longer depends on regenerated chunk IDs or evidence revision IDs. Those fields and vectors update in place while the stable FTS surrogate row is preserved. Changed text still follows full atomic publication. This avoids rebuilding the trigram index for unchanged passages. Identical vector/evidence row updates are skipped.

A controlled synthetic replay used 200 documents / 2000 chunks in separate database files. Each new pass regenerated chunk IDs. With unchanged text, the previous implementation emitted 141.01 MB of WAL in 200 commits (0.629 s); the new 32-document replay groups emitted 9.64 MB in 7 commits (0.041 s). When every text changed, the figures were 141.95 MB (0.644 s) versus 52.13 MB (0.584 s). Seeding was excluded; autocheckpoints were disabled during both timed passes to compare WAL volume. Retrieval row counts were verified. Physical writes can be delayed/coalesced by the OS, so these figures measure WAL traffic, not SSD lifetime writes or whole-corpus throughput. Actual live batches depend on concurrent completions and can be smaller.

Repeated folder re-chunk/reparse requests with the same options now share their active pass; conflicting options do not start another pass. Unload stops directory iteration before scheduling further child work.

Regression tests cover grouping, savepoint failure isolation, unchanged-text retrieval with new IDs/evidence, durability before acknowledgment, shutdown draining, and deletion races. All changes remain inside the standalone Knowledge plugin and public DSH hooks.
