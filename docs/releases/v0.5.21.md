# v0.5.21 — Visible folder rebuild progress and bounded batching

Folder re-chunk/reparse passes now enumerate saved descendants once and report their own processing meter. Starting a rebuild replaces the previous settled sync meter for that base. The panel labels re-chunking and re-parsing explicitly, reports completed/total, queued/running and failures, and uses the existing rolling two-minute completion estimator. It does not invent an ETA before sufficient samples exist.

Up to four rebuild producers feed the existing bounded RAM publication buffer, allowing concurrent completions to share a SQLite transaction. The single writer, durable staging, savepoint isolation, commit-before-acknowledgment, shutdown draining, and RAM admission bounds remain in place. This is bounded asynchronous concurrency, not multiple SQLite writers. Nested directory metadata is enumerated once rather than repeatedly scanning the entire base. Unchanged canonical text continues to retain its full-text index rows; changed chunk boundaries still require durable index updates. This does not promise zero SSD writes or eliminate writes proportional to changed data.

Regression coverage checks nested progress, stale sync replacement, bounded producers, queued counts, failure reporting, and completed counts. The running plugin must be reloaded to use the new code; reloading interrupts an in-flight rebuild, so no automatic runtime reload is performed while that pass is active.
