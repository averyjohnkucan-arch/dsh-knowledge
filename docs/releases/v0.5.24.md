# v0.5.24 — Preserve batching under writer load

Completed documents arriving while a publication is queued now receive a fresh bounded collection window after that publication completes. Previously, the writer immediately drained those arrivals, producing a long sequence of singleton transactions under load. The existing 32-document / 8-MiB flush targets and 64-document / 64-MiB pending bounds remain. Acknowledgement still follows commit, and shutdown drains accepted work.

Internal-base duplicate detection uses a base-scoped indexed content-hash lookup instead of reading every source body per file. External-folder imports continue to skip content deduplication. Base deletion reads headers only; restoring a base reads one source body at a time. Metadata list order is explicit and stable.

## Validation and limits

The full suite passed 730 tests with one skipped before the additional deletion/restore read guards. The affected service/storage suites passed again afterward; type checking and build passed. New tests cover arrivals during an occupied writer and scoped duplicate lookup without full-library scans.

On one resumed live external-folder import, 248 of 261 publication batches contained 32 documents. The pass finished with 50,255 documents accounted for and zero failures. A final 1,287-document sample recorded 1,514,541,056 process-accounted write bytes (about 1.12 MiB per published document). This is not a controlled before/after write-volume benchmark: document sizes varied and the sample included checkpoints. SSD-controller bytes and total write amplification were not measured. Full-text indexing still requires substantial durable writes; this release does not claim all remaining I/O overhead is eliminated.

Only the standalone Knowledge plugin changed. No DSH host changes or RAM-disk dependency are required.
