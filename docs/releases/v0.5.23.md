# v0.5.23 — Batch fresh-import index writes

This release targets new imports, distinct from the unchanged-text rebuild fixes in v0.5.22. Full-text indexing, transaction logging, status metadata, and new durable content still require SSD writes. It does not cap instantaneous MB/s or remove necessary data writes.

Fresh chunk rows are inserted with one SQL statement per group of at most 64 rows (832 bound parameters). Existing per-document savepoints, rollback isolation, triggers, stable FTS row IDs, and commit-before-acknowledgment are preserved. A failed group cannot leave half of a document searchable.

Completed documents collect in RAM for up to 50 ms, flushing at 32 queued documents or the existing 8 MiB estimated-input target. Pending admission remains capped at 64 documents / 64 MiB. A larger lightweight read-ahead window supplies those batches without increasing the shared parser/OCR concurrency. Only supported text formats whose files are at most 1 MiB qualify. Larger files and PDFs keep the old heavy-file limit. The maximum total window is four times the existing processing concurrency (32 here).

`GET /knowledge/storage-writes` reports batches, successfully published documents, batch-size histogram and pending estimated RAM bytes. It requires the same authenticated local-management boundary as accelerator management. It contains no document text, paths or credentials.

## Reproduce storage-write measurement

From a development checkout with dependencies installed:

```sh
npm run benchmark:writes -- --source=/path/to/markdown --baseline=24c54c9 --output=/tmp/import-write-report.json
```

The benchmark reads the first 256 sorted Markdown sources without modifying them and creates isolated temporary SQLite databases. It includes the actual DomainStore placeholder, resumable source-text update, RAM publication, and signature-update paths. A simulated 5-ms parser delay is identical in all variants. It excludes real OCR, model calls and artifact files. Automatic WAL checkpoints are disabled during the timed region so WAL byte totals can be compared; FTS integrity and chunk counts are checked. Measured WAL bytes are not physical device writes.

An initial controlled run used 6,847,378 source bytes and 4,219 chunks:

| Variant | WAL bytes | Time | Publication batches |
| --- | ---: | ---: | --- |
| v0.5.22, 8 producers | 121,482,352 | 2.084 s | 32 batches of 8 |
| v0.5.23, 8 producers | 112,443,072 | 2.737 s | 32 batches of 8 |
| v0.5.23, 32 lightweight producers | 79,981,592 | 0.875 s | 8 batches of 32 |

A second replay using randomly generated UUIDs measured 127,328,632 → 82,573,072 WAL bytes (about 35% less), confirming that the result does not depend on the compact synthetic identifiers.

The combined change reduced WAL volume about 34% in this fresh-import replay. Extending collection alone with only eight producers was slower; the lightweight read-ahead change is part of the implementation. The benchmark includes a control for that case. Results depend on source sizes, arrival timing and batch fullness. Live checks should compare actual published counts and batch histograms, not one short write-rate sample.

SQLite's [FTS5 source](https://raw.githubusercontent.com/sqlite/sqlite/master/ext/fts5/fts5_main.c) documents RAM flushes at savepoints. Removing savepoints alone did not improve the measured workload, so that experiment was discarded. FTS tokenizer, query semantics, merge configuration and durability settings remain unchanged. All changes remain within the standalone Knowledge plugin.
