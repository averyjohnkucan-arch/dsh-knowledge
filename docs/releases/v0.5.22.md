# v0.5.22 — Reduce rebuild write amplification

Re-chunking retains a passage ID when its position, text, and indexed search text match the previous passage. Identity lookup excludes vectors. This preserves existing citations and avoids rewriting unchanged chunk rows. Partial document publication retains exact neighbour rows and their FTS row IDs; all-changed documents still use the narrow document-index bulk replacement. Savepoint isolation, atomic publication, and post-commit vector-cache updates are retained.

Frequently updated document headers no longer share a large SQLite row with source text. The plugin adds a separate source-text table and converts existing inline text lazily on the next document write, inside a savepoint. Reads support both layouts; there is no startup-wide rewrite. Exact source text is not updated again when unchanged. Header failure rolls back source changes; document deletion cleans up the separate text. This storage layout requires v0.5.22 or later to read converted bodies; do not downgrade without restoring a compatible backup.

The incomplete document marker remains durable. Rebuilding does not save an empty candidate copy of the full source text before any embedding results exist. Actual completed embedding batches still stage durably, and unchanged candidate metadata is not rewritten for each batch. Completed publications remain bounded in RAM and resolve only after the SQLite commit.

A missing parsing sidecar now falls back to surviving saved text for an explicit re-chunk request. This avoids repeated missing-file retries when text is available. Corrupt/mismatched sidecars still fail, and absent text cannot erase a good generation. A fallback generation drops the invalid processing-sidecar reference rather than advertising evidence that no longer exists.

## Isolated write replay

200 documents / 2,000 chunks, four publications per transaction in both versions. Includes incomplete metadata and the former empty staging step. Seeding is outside timing; automatic checkpoints are disabled in both timed regions to compare WAL bytes. Exact retrieval counts are checked using FTS MATCH. These are WAL-volume comparisons, not physical SSD writes or whole-library throughput.

| Changed chunks per document | Previous WAL bytes | New WAL bytes, converted storage | New WAL bytes, first legacy conversion |
| --- | ---: | ---: | ---: |
| 0 / 10 | 54,684,792 | 2,125,952 | 19,982,032 |
| 1 / 10 | 131,980,112 | 29,956,552 | 48,653,112 |
| 10 / 10 | 132,169,632 | 94,924,832 | 118,219,312 |

Unchanged-text traffic falls about 96% after conversion (63% including the first conversion); one-chunk edits fall about 77% (63% during conversion). Fully changed text still incurs necessary text/index writes. Live rates depend on document sizes, changed boundaries, checkpoints and concurrent work; no fixed SSD-rate guarantee is made.

All changes are contained in the standalone Cordis Knowledge plugin. No Harness core changes or external RAM disk are required.
